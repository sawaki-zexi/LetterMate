# LetterMate 产品需求

**状态：** 当前产品基线
**更新日期：** 2026-08-10

## 1. 产品目标

LetterMate 是个人信息发现工作台，帮助学生和开发者主动浏览技术内容，并通过每日邮件被动获知真正重要的变化。

产品聚焦三类信息：

- 用户用一个关键词建立的持续监控；
- 无需用户配置的 AI 与技术热点；
- 用户主动关注的公开平台博主。

所有进入统一 Feed 或每日邮件的内容都必须具备可回溯的原始 HTTP(S) 链接，并经过正文补全、事实支持、历史增量和去重。产品优先保证质量；没有合格内容是正常结果。

## 2. 当前基线

当前 Alpha 已完成：

- 完整关键词 Topic 的创建、编辑、软删除、手动刷新和 6/12/24 小时自适应调度；
- AI、技术、软件、工程和研究范围内的自动趋势发现；
- Web、社交、Feed、社区、视频、代码和论文等多类来源；
- 来源证明、正文补全、事实支持、精确与近似去重和中文内容生成；
- `hot | quality` 分类、跨 Topic/Trend/Creator 去重的统一 Feed、完整来源合并、已入库内容搜索、来源/时间筛选和日期分组；
- RSS/Atom、X、Bilibili、YouTube 与 Bluesky 的名字/Handle/主页解析、身份预览与确认、暂停/恢复/取消、手动与每日同步及 Creator Feed 来源；
- Feed 卡片的“感兴趣 / 减少推荐”持久化反馈、切换、取消和跨来源合并状态；
- 基于活动关键词、合格博主内容和显式反馈的兴趣记忆与个性化排序；
- 对现有候选的相邻技术兴趣识别、约 10% Feed 上限和负向偏好排除；主动构造相邻领域候选仍待真实效果基线稳定后实施；
- 每日研究简报偏好、预览、本地时间调度、带引用冻结快照、失败重试和最近运行状态；
- 可选生产事务邮件投递；推荐使用支持幂等键的 Resend HTTP API，SMTP 保留为兼容模式；未配置时明确显示并停用邮件调度，不影响 Feed；
- 用户所有权边界、运行租约、持久化运行状态和默认离线测试。

真实登录、服务端 Session Cookie、CSRF、结构化运行事件、低基数运行指标、数据库备份、隔离恢复验证和容器部署基线已实现；生产上线前仍需完成目标环境 TLS、秘密存储、指标采集与告警、定时加密外部备份和周期恢复演练。

## 3. 用户体验

### 3.1 关键词监控

- 用户只输入 1-100 字符的关键词，不选择监控类型，也不配置事件规则。
- 对 `gpt-5.7` 等具体对象，系统优先发现正式发布等重大事件，并持续追踪后续重要更新。
- 对 `AI Agent` 等领域关键词，系统持续发现该领域的重要内容。
- 系统可以自动调整检索重点，但不能扩大完整关键词、型号或版本边界。
- 仅改变大小写、空格或连字符且不改变含义的形式可以视为同一关键词；`gpt-5.7.1` 不得作为 `gpt-5.7` 的命中。
- 用户可以编辑、暂停或删除监控。历史 Feed 永久保留，并显示发现时的关键词。

### 3.2 自动热点

- 系统默认发现 AI、技术、软件、工程和研究范围内的重大变化。
- 趋势榜单只产生搜索种子，不直接生成 Feed 条目或邮件内容。
- 候选必须经过主发现管线并取得正文或一手支持材料。
- 自动热点可以整体暂停；缺少合格内容时允许为空。

### 3.3 博主关注

- 用户只需输入博主名字、Handle、公开账号主页 URL 或 RSS/Atom URL。系统在当前支持且已配置的平台中解析候选，展示平台、头像、Handle、简介、认证状态和主页链接；用户确认后才创建关注。
- 完整主页 URL 和 RSS/Atom URL 也必须先显示单一身份预览，不能未经确认直接创建。候选身份来自平台或 Feed 响应，AI 只能提示疑似冒充风险，不能猜测账号或链接。
- 平台能力列表显示 `enabled | not_configured`。已实现但缺少必要 Key 的平台继续显示“未配置”，但不能搜索候选或创建关注；产品不承诺任意平台均可关注。
- RSS/Atom、X、Bilibili、YouTube 与 Bluesky 关注已实现。YouTube 支持频道名、Handle 和频道主页解析，固定稳定 `channelId` 并同步 uploads playlist 中的公开视频。Bilibili 支持 UP 主身份、公开视频、公开动态、专栏和动态转发；转发保留原作者、原帖链接和原文上下文，缺失可解析原帖的转发不收录。Bluesky 支持显示名、Handle 和主页解析，固定稳定 DID，并同步公开原创、引用、转发和带父帖上下文的回复；缺失父帖的回复不收录。
- 同一博主在不同平台的账号是独立关注。候选结果可多选并一次创建多个关注，但每个平台账号独立运行、暂停和报告错误。
- 博主同步区分成功、部分同步和失败。部分同步必须保留已获取的合格内容，展示受影响的来源并允许重试；来源错误只返回安全提示，不展示 provider 原始响应。
- 系统只获取公开内容，不使用个人 Cookie、模拟登录或非授权抓取。
- 博主内容包括原创、连续帖、高质量转发和具有独立阅读价值的回复。转发必须保留原作者并标记转发关系；回复必须携带原帖上下文；简短社交回复仍被过滤。
- 博主详情页保留成功获取并完成中文标题、中文摘要生成的全部有效公开内容，包括 AI 判定为低优先级的内容；无效、无法验证、重复或未能完成中文化的单条内容不保存。单条中文化失败不能中断整个博主同步，系统在后续同步中重试。
- 只有具有明显信息增量的内容进入统一 Feed、显示中文推荐理由并参与每日邮件筛选。转发原文和回复父帖上下文作为来源证据保留原始语言，不要求翻译。
- 后续手动或每日同步自动回填历史归档中的非中文标题或摘要，每次最多处理 30 条，避免一次运行无界消耗 AI 配额。
- 关注绑定平台稳定账号 ID，不依赖可变展示名或 Handle。账号改名后继续同步；删除、封禁或转私密时标记暂不可用、保留历史并自动重试，不能自动取消关注。
- 用户可以暂停或取消关注，历史内容继续保留。

### 3.4 兴趣与探索

- 用户通过“感兴趣”和“减少推荐”提供显式反馈；不提供 1-5 分评分。
- 反馈绑定合并后的内容键。重复选择保持幂等，选择当前状态即取消，选择另一状态即切换；刷新或重新登录后状态仍保留。
- 关键词监控和博主关注本身是正向兴趣信号；博主内容只有在至少两篇内容、至少两个自然日中重复出现的高置信主题或实体才能自动进入兴趣画像，单篇标签和内容类型不能自动沉淀为长期兴趣。显式反馈权重更高，未反馈不视为负向信号。
- “减少推荐”立即降低当前条目的排序，即使该内容尚无兴趣标签；存在高置信标签时再局部降低相似内容。反馈成功后客户端重新获取 Feed 和兴趣记忆，并显示已生效状态。
- MVP 不根据单纯点击自动推断偏好。
- 个性化影响自动热点、领域型关键词结果和普通推荐的选择与排序，但不降低质量门槛。
- 用户明确创建的关键词监控和博主关注不会被偏好静默取消或隐藏。
- Feed 最多约 10% 为探索推荐。探索内容来自用户未明确排斥的相邻技术领域，使用相同质量门槛；候选不足时允许为零。
- 探索内容在 Feed 中明确标记，不进入每日邮件。
- 语义召回上线前必须通过时间正确的 rolling-split 准入评估；标签缺失和冷启动不能被计为语义缺口，数据不足时不得启用向量召回。

### 3.5 浏览器 Feed

- Feed 合并关键词、自动热点和博主高价值内容；同一原始内容只显示一次，并标明原作者、平台以及哪些已关注博主发布或转发过。多个博主或平台命中只能提高排序信号，不能绕过质量筛选。
- Feed 用于主动浏览，支持已入库内容搜索、时间范围、来源和 `hot | quality` 筛选。
- 卡片显示中文标题、摘要、推荐理由、平台、作者和原始链接。
- 搜索只查询当前用户已经持久化的内容，不触发外部发现。
- 外部链接在新标签页安全打开；桌面、平板、手机和 320px 视口不得水平溢出。

### 3.6 每日研究简报

- 用户可以填写独立于登录邮箱的简报收件地址。LetterMate 只验证该地址可以收信，不请求邮箱密码、SMTP 凭据或 Gmail/Microsoft 代发授权。
- 收件地址具有 `unverified | pending | verified | suppressed` 状态；只有当前 `verified` 地址才能启用或调度每日邮件。修改地址必须撤销旧验证结果和未使用的验证链接，同时立即暂停每日邮件；新地址验证完成后仍需用户显式重新启用。
- 验证链接使用高熵、短时、一次性 Token；数据库只保存 Token 哈希。请求和重发按用户、规范化地址和客户端边界限频，确认失败不得泄露其他账户是否使用该地址。
- 已验证用户可以向当前收件地址发送明确标注的测试邮件。测试发送使用独立记录和队列，不创建 `DigestRun`、不推进上次成功边界；请求按用户限频，并在短时间桶内对同一地址幂等复用。
- 用户可以启用每日邮件并设置本地发送时间。
- 邮件汇总自上次成功发送后新增的关键词更新、重要博主内容和自动热点。
- 内容按重要性和用户兴趣统一排序，最多 10 条，不为不同来源强制分配名额。
- 每条内容包含中文结论、证据、不确定性、后续关注点、来源平台、发布时间和至少一个已验证的原始 HTTP(S) 引用。
- 简报生成和投递重试必须复用已冻结的引用快照；生成失败时回退为可读的链接摘要，不发送无引用结论。
- 每个 `DigestRun` 在创建时冻结当时的已验证收件地址。设置变化、地址重新验证和投递重试都不得改写该运行的地址；没有冻结地址的运行不得投递。
- 每封正式简报的文本和 HTML 都提供清晰退订链接，并发送 RFC 8058 `List-Unsubscribe` 与 `List-Unsubscribe-Post` 头。链接使用随机、可撤销的令牌 ID 和 HMAC 签名，不包含用户 ID 或邮箱。
- 公开退订不要求登录，重复或并发请求保持幂等，并立即设置 `enabled=false`；历史 `DigestRun`、邮件和 Feed 数据保留。修改收件地址或从关闭状态显式重新启用时轮换令牌，使旧邮件链接失效；重新启用仍要求当前地址已验证且未被抑制。
- Resend 投递事件必须使用原始请求体和 Svix 签名头验签，并按供应商事件 ID 长期幂等。系统只通过已持久化的供应商消息 ID 关联本地验证邮件、测试邮件或正式简报，不信任 Webhook 中的收件地址。
- 明确永久退信、投诉或供应商抑制会立即把当前匹配地址置为 `suppressed` 并关闭每日邮件；临时退信、延迟和一般失败不自动抑制。被抑制地址不能重新验证或启用，用户必须更换地址并重新完成验证。
- 启用 AI 时，模型只能通过服务端分配的稳定引用 ID 选择当前条目的已验证来源，不能生成 URL、跨条目引用或增加来源之外的事实；任何校验失败都必须整批回退。
- 探索内容不进入邮件；没有合格新内容时不发送邮件。
- 同一内容不得因重复发现、摘要重算或发送重试而重复投递。
- 邮件失败可以重试，但失败不能推进“上次成功发送”边界。
- Resend HTTP API 使用稳定 DigestRun 键作为供应商幂等键。SMTP 兼容模式使用确定性 `Message-ID` 尽力避免重复，但在“服务端已接受、客户端未收到确认”时不能提供严格零重复保证。

## 4. 共同质量与安全规则

- 网页必须取得正文；视频需要足够的说明、章节、字幕或文字稿；论文至少需要标题、作者和摘要；代码内容需要 README、Release Notes 或实质讨论。
- 发布、上线、融资、政策变化等核心事实必须得到正文或一手记录支持。传言、冒充来源、标题正文冲突和无支持声明不得入库。
- AI 只能从服务端验证过的候选池中选择 URL，不能新增、改写或猜测链接。
- 按平台内容 ID、规范化 URL、标题和内容指纹去重，并与用户历史比较信息增量。
- 用户数据执行所有权检查；跨用户访问不暴露资源是否存在。
- Web 只调用 LetterMate API。AI Key、邮件凭据、平台凭据和鉴权头只保留在服务端。
- 产品不展示可信分数、证据数量、来源排名、“已核实”标签或内部 AI 判断。
- 外部抓取必须防 SSRF，并限制 MIME、大小、重定向和超时。

## 5. 验收标准

1. 用户只输入关键词即可开始监控；系统能兼顾具体对象的重要事件和领域内容，并保持完整关键词与版本边界。
2. 自动趋势只提供种子；无正文或事实支持的候选不能进入 Feed 或邮件。
3. 用户可用名字、Handle、主页 URL 或 RSS/Atom URL 查找公开博主，核对平台身份后关注、暂停和取消；博主详情页保留全部已完成中文标题和摘要的有效公开内容，高价值内容进入统一 Feed。
4. 同一内容经关键词、趋势、多个博主或多个平台发现时只显示一次，并保留原作者及全部发现、发布或转发来源；邮件选择和运行记录不重复包含同一内容。
5. “感兴趣”提高相似合格内容的相对优先级；“减少推荐”立即降低当前条目及有标签的相似内容优先级，即使当前条目没有标签也必须生效。两者不隐藏明确订阅，也不改变质量门槛。
6. Feed 的探索内容不超过约 10%，明确标记且不进入每日邮件；候选不足时不以低质量内容补足。
7. 每日邮件按用户本地时间发送最多 10 条；无合格内容不发送，失败不推进成功边界，重试复用同一快照和确定性消息 ID；收件人可从任意正式简报一键退订；永久退信、投诉和供应商抑制会停止未来发送，用户只能更换并验证地址后显式重新启用。
8. 每条博主归档、Feed 和邮件内容都有有效原始链接、中文标题、中文摘要和可回溯来源；只有 Feed 和邮件内容必须显示推荐理由。
9. 所有新增资源执行用户所有权检查，外部密钥和内部判断不泄漏。
10. 默认测试不联网；Prisma 生成与迁移、lint、typecheck、单元/集成测试、构建和端到端测试通过。

## 6. 本期不包含

- 通用社会新闻热点；自动发现仍聚焦 AI 与技术领域。
- 浏览器通知、独立站内通知中心、短信、系统 Push、微信和即时逐条邮件。
- 每周或任意周期摘要；MVP 仅提供每日邮件。
- 私密账号、登录后内容、付费墙绕过、个人 Cookie 抓取、模拟登录和验证码绕过。
- 自动替用户关注外部账号、点赞、评论或执行其他社交操作。
- 仅基于点击的隐式画像、向量化用户画像或用户可见的内部评分。
- 用户自定义来源优先级、黑白名单和复杂监控规则。
- 对任意外部平台的通用关注保证；每个平台必须有已实现且合规可运行的 Creator Connector。

## 7. 交付前提

真实登录、服务端 Session Cookie 和 CSRF 防护已实现。开发环境默认保留 `ALLOW_DEV_IDENTITY=true` 以兼容本地和 E2E 流程；生产环境必须配置 `SESSION_SECRET`、`CSRF_SECRET` 并设置 `ALLOW_DEV_IDENTITY=false`。API 与 Worker 已输出脱敏结构化日志、统一 trace/run 标识、队列快照和低基数 Prometheus 指标，并支持健康探针、优雅退出和容器部署。生产 Compose 已提供默认仅绑定本机的 Prometheus 抓取与初始告警规则；目标环境仍需接入 Alertmanager、通知渠道和日志聚合。数据库工具已实现 custom-format 备份、SHA-256 清单、14 日/8 周/12 月分层保留和隔离恢复验证；生产部署仍需配置 TLS、秘密存储、定时备份、加密外部副本和周期恢复演练。生产主库恢复必须经过停机和人工审批。生产邮件只有在完整服务端 Resend 或 SMTP 配置存在时启动；未配置不是系统故障，邮件凭据不得进入浏览器。

# LetterMate 刷新反馈、趋势监控与时间筛选设计

**状态：** 已确认
**日期：** 2026-07-28
**范围：** 发现页刷新体验、关键词精准监控、外部趋势榜单驱动的自动热点、发现内容时间筛选与分组

## 1. 目标

本次改动解决三个相互关联的问题：

1. 发现页点击或移动端下拉刷新后立即提供可见反馈，并在异步发现任务完成后准确提示新增内容条数。
2. 用户 Topic 按完整关键词精准追踪新内容；系统同时从外部趋势榜单发现无需用户预先指定的技术、AI、产品和研究热点，并在入库前验证正文和核心事实。
3. 所有发现内容列表统一支持快捷时间筛选，并按自然时间段分组展示。

本设计不新增用户可见的可信等级、来源排名、证据数量、质量分数或“已核实”状态。趋势榜单中的排名只用于一次运行内控制候选顺序，不持久化、不展示，也不作为事实真实性证明。

## 2. 总体架构

系统采用两条发现管线，共享现有连接器、正文补全、去重、质量评审和内容生成能力。

```text
关键词精准追踪
User Topic
  -> 精准查询计划
  -> 多源定向搜索
  -> 关键词命中校验
  -> 统一质量与事实支持过滤
  -> DiscoveryItem

自动趋势发现
External Trend Sources
  -> TrendSeed 标准化与去重
  -> 技术垂直分类和实体提取
  -> 基于种子的精准查询计划
  -> 多源正文与一手信息搜索
  -> 统一质量与事实支持过滤
  -> RadarItem

DiscoveryItem + RadarItem
  -> Unified Feed API
  -> 时间筛选
  -> 时间分组
  -> React Web
```

趋势榜单只提供搜索种子。任何榜单标题、热词或排名都不能直接转换为最终发现条目；系统必须继续查找可阅读正文、一手平台记录、官方发布、代码 Release、论文或其他能够支持核心事实的材料。

## 3. 关键词精准监控

### 3.1 查询语义

用户创建 Topic 时仍只输入一个关键词。系统在现有 AI 扩展结果之外生成确定性的匹配策略：

- `exactPhrase`：原始关键词的规范化完整形式，例如 `gpt-5.7`。
- `requiredTokens`：不能在扩展时丢失的标识符、产品名和版本号。
- `confirmedAliases`：仅包含不会扩大主题边界的大小写、空格、连字符和官方别名变体。
- `searchIntents`：发布、更新、公告、文档、Release、论文、作者说明和变更记录。

版本号、型号、项目名和带标点的标识符必须保持整体。例如 `gpt-5.7` 不得被宽化为 `GPT`、`AI model` 或“人工智能”。AI 生成的查询如果丢失必要标识符，查询计划在进入连接器前将其丢弃。

### 3.2 候选命中规则

精准 Topic 的候选进入质量管线前必须满足以下条件之一：

- 标题或正文包含完整精确短语；
- 标题或正文包含经确认的别名，并保留所有必要标识符；
- 一手平台的结构化字段明确标识同一发布、仓库、论文或产品版本。

仅在搜索摘要、标签页、分类页或无正文页面中出现关键词不算命中。候选仍需通过时间窗口、来源证明、正文完整性、历史增量和去重规则。

### 3.3 调度

Topic 继续使用现有 6、12、24 小时自适应周期：

- 新建后立即执行；
- 连续产生有效新增内容时缩短周期；
- 连续无新增时延长周期；
- 手动刷新不改变自动周期和长期 streak；
- 同一 Topic 同时最多一个运行中任务，运行中再次刷新只登记一次待处理手动刷新。

## 4. 外部趋势榜单监控

### 4.1 趋势来源

首批趋势适配器使用平台提供的榜单或结构化热门入口：

| 趋势来源 | 入口 | 启用条件 |
| --- | --- | --- |
| X Trends | TwitterAPI.io `GET /twitter/trends`，按配置的 WOEID 获取 | `TWITTERAPI_IO_API_KEY` |
| Hacker News | 官方 Top Stories | 无 Key |
| YouTube | Data API `videos.list` 的 `mostPopular` | `YOUTUBE_API_KEY` |
| Reddit | OAuth API 的 Hot 列表，限定技术相关社区 | Reddit OAuth |
| Bilibili | 公共热门视频接口 | 公共接口可用 |
| Google Trends | 可配置的 Trending RSS | 配置 Feed URL |

GitHub Trending 不纳入首批自动趋势来源，因为 GitHub 没有稳定的官方 Trending API。GitHub 仓库和 Release 继续作为关键词精准搜索和趋势种子验证来源。

每个趋势适配器实现独立接口：

```ts
interface TrendSource {
  readonly id: string;
  readonly label: string;
  isEnabled(): boolean;
  collect(input: TrendWindow, signal: AbortSignal): Promise<TrendSourceResult>;
}
```

适配器只返回标准化 `TrendSeed`，不调用最终内容生成，也不保存外部完整响应。

### 4.2 TrendSeed

`TrendSeed` 保存最小化、可审计的信息：

- 所属用户和 TrendRun；
- 趋势来源 ID、平台和外部 ID；
- 榜单标题或热词；
- 原始 HTTP(S) URL；
- 规范化指纹；
- 平台给出的可用发布时间和系统发现时间；
- 由垂直分类阶段提取的规范化查询词。

平台排名、内部选择分数、完整响应和敏感请求信息不持久化。

### 4.3 垂直筛选和验证

自动趋势只面向技术、AI、软件产品和研究内容。趋势运行按以下顺序处理：

1. 从已启用榜单并发拉取有限候选。
2. 按平台外部 ID、规范化 URL 和标题指纹去重，并跳过近期已经处理过的种子。
3. 使用结构化 AI 输出判断是否属于目标垂直领域，并提取不得丢失的实体、产品名和版本标识。
4. 对通过的种子构建与 Topic 相同的精准查询计划。
5. 复用 `ConnectorRegistry` 从网页、社交、视频、社区、代码和论文来源查找正文与一手材料。
6. 复用统一质量管线完成正文补全、事实支持判断、近似去重、来源多样性和中文内容生成。
7. 只有最终通过的内容才写入 `RadarItem`。

趋势源失败互相隔离。至少一个趋势源成功且后续管线完成时，TrendRun 可以成功并返回空结果；所有趋势源失败或 AI 阶段失败时，运行失败且不保存半成品 RadarItem。

### 4.4 调度

每个用户拥有一个自动创建的 `TrendMonitor`：

- 默认每 4 小时运行一次；
- PostgreSQL 的 `nextRunAt` 是调度真实状态；
- 调度器使用租约和确定性任务 ID 防止重复运行；
- 发现页手动刷新可以触发一次 `manual` TrendRun；
- 手动刷新不改变 4 小时自动周期；
- 趋势任务正在运行时再次刷新，只登记一次待处理手动刷新。

## 5. 虚假信息与低质量过滤

趋势出现不代表事实成立。统一质量管线增加内部的“核心事实支持”判断，但不产生用户可见状态。

### 5.1 接受条件

候选需要同时满足：

- 正文、平台记录或结构化发布信息能够支持标题中的核心事实；
- 时间处于本次发现窗口内；
- URL 和来源证明有效；
- 内容不是转载聚合、登录页、分类页、广告页或只有搜索摘要；
- 对 Topic 内容，正文满足精准关键词匹配策略；
- 对趋势内容，正文明确对应 TrendSeed 提取出的实体或事件。

官方公告、作者原帖、维护者说明、代码 Release 和论文记录可以作为一手材料。短内容不会仅因长度被拒绝，但必须包含实质性新增信息和可回溯平台记录。

### 5.2 拒绝条件

以下内容直接拒绝：

- 标题声称发布、上线、融资或政策变化，但正文没有对应事实；
- 纯猜测、传言、戏仿、虚构或无法确定主体的内容；
- 正文与标题明显矛盾；
- 只引用其他帖子且没有新增信息；
- 只在榜单名称或搜索摘要中出现关键词；
- AI 试图引用候选池之外的 URL。

AI 评审返回的支持判断只在运行内存在。数据库和 API 不保存或返回可信等级、支持数量、来源评分或内部判断理由。

## 6. 数据模型

### 6.1 Topic 运行摘要

`Topic` API DTO 增加 `lastRun`，来自最新的 `DiscoveryRun`：

```ts
interface RunSummary {
  id: string;
  trigger: 'initial' | 'manual' | 'scheduled';
  status: 'queued' | 'running' | 'succeeded' | 'failed';
  startedAt: string;
  finishedAt: string | null;
  newItemCount: number | null;
}
```

运行未结束时 `newItemCount` 为 `null`。该摘要用于页面检测某次手动刷新何时完成，不暴露连接器内部错误或敏感信息。

### 6.2 趋势表

新增：

- `TrendMonitor`：用户、运行状态、下一次执行时间、4 小时间隔、租约和待处理手动刷新。
- `TrendRun`：用户、触发方式、状态、开始/结束时间、候选数、录取数、新增数和安全错误。
- `TrendSeed`：最小化榜单种子、指纹、来源 URL 和提取查询词。
- `RadarItem`：用户所有的最终趋势发现内容，字段与 `DiscoveryItem` 的用户可见内容一致。

所有表都保持用户所有权检查。`RadarItem(userId, canonicalPrimaryUrl)` 唯一，避免不同 TrendRun 重复保存同一内容。

### 6.3 Feed DTO

统一 Feed 使用判别联合：

```ts
type FeedItem =
  | (DiscoveryItem & { origin: 'topic'; topicId: string })
  | (RadarItem & { origin: 'trend'; topicId: null });
```

卡片可以显示“关键词追踪”或“趋势发现”，但不显示榜单排名、可信标签或内部评审结果。

## 7. API

### 7.1 时间范围

`GET /api/v1/feed` 的 `range` 改为：

- `1d`：近 24 小时；
- `3d`：近 3 天；
- `7d`：近 7 天；
- `30d`：近 30 天，默认；
- `90d`：近 90 天；
- `all`：全部历史。

可与现有 `topicId`、`kind` 组合，并增加 `origin=all|topic|trend`。当指定 `topicId` 时，`origin` 必须是 `all` 或 `topic`。

服务端按 `publishedAt ?? discoveredAt` 过滤和倒序排序。Topic 条目与 Radar 条目分别查询后，在服务端合并并稳定排序；浏览器不加载范围外的历史数据。

### 7.2 趋势接口

新增：

- `GET /api/v1/trends/status`：返回当前用户的 TrendMonitor 和最新 TrendRun 安全摘要；
- `POST /api/v1/trends/refresh`：登记一次手动趋势刷新，返回 `202`；
- `GET /api/v1/items/:id`：在保持用户所有权检查的前提下同时支持 Topic 和 Radar 条目。

现有 `POST /topics/:id/refresh` 保持兼容，但返回的 Topic 包含 `lastRun` 摘要。

## 8. 刷新交互

### 8.1 发现页

顶部刷新按钮和移动端下拉刷新调用同一协调逻辑：

- 选择某个 Topic 时，只刷新该 Topic；
- 查看全部主题时，刷新当前用户的所有 Topic，并触发一次趋势刷新；
- 查看“趋势发现”时，只刷新 TrendMonitor；
- 查看“关键词追踪”时，只刷新 Topic。

手动刷新开始后：

1. 刷新图标立即旋转；
2. 移动端下拉指示器随拖动距离显示，超过阈值并松手才触发；
3. 页面显示非阻塞状态条，例如“正在更新 3 个主题和趋势榜单”；
4. Feed 和 Topic/Trend 状态按 1.5 秒轮询；
5. 前端只接受请求开始时间之后、`trigger=manual` 的终态运行摘要；
6. 所有目标进入终态后重新请求 Feed 并汇总 `newItemCount`。

完成提示：

- 全部成功且有新增：`刷新完成，新增 6 条内容`；
- 全部成功且无新增：`刷新完成，暂无新增内容`；
- 部分失败：`部分更新失败，已新增 4 条内容`；
- 全部失败：`刷新失败，已保留现有内容`。

提示使用 `aria-live="polite"`。刷新不使用全屏遮罩，用户仍可浏览已有内容。

### 8.2 主题页

每个 Topic 行拥有独立刷新状态：

- 只有当前 Topic 的刷新图标旋转和禁用；
- 其他 Topic 仍可操作；
- 完成后使用同一提示组件显示该 Topic 的新增条数；
- Topic 运行失败时保留旧内容并显示安全错误。

### 8.3 动画和触摸边界

- 使用现有 Lucide `RefreshCw`，不增加自绘 SVG；
- 图标按钮保持固定尺寸，旋转不引发布局位移；
- `prefers-reduced-motion: reduce` 下停止连续旋转，改用静态状态变化；
- 下拉刷新只在触摸设备、页面滚动位置为顶部且主要手势为向下纵向移动时生效；
- 小于触发阈值、横向手势和表单控件内手势不触发刷新。

## 9. 时间筛选与分组

发现页顶部使用原生下拉选择器，提供：

- 近 24 小时；
- 近 3 天；
- 近 7 天；
- 近 30 天；
- 近 90 天；
- 全部历史。

默认“近 30 天”。全部、热点、优质、Topic、趋势发现视图共享当前时间范围。

API 返回范围内的排序结果后，前端按 `publishedAt ?? discoveredAt` 分组：

- 今天；
- 昨天；
- 近 3 天；
- 近 7 天；
- 本月更早；
- 更早。

分组互斥，空分组不渲染。分组标题使用紧凑样式，不采用卡片容器，也不改变 DiscoveryCard 的固定布局。

时间筛选只适用于具有发布时间或发现时间的内容列表；Topic 管理列表和来源状态列表不是内容 Feed，不增加无意义的时间筛选。

## 10. 配置

新增服务端配置：

```env
TREND_MONITOR_ENABLED=true
TREND_INTERVAL_HOURS=4
TREND_X_WOEIDS=1
TREND_YOUTUBE_REGION=US
TREND_REDDIT_COMMUNITIES=MachineLearning,LocalLLaMA,programming,technology
TREND_GOOGLE_RSS_URLS=
```

- `TREND_MONITOR_ENABLED` 控制自动趋势调度，关闭后仍保留已发现历史；
- `TREND_INTERVAL_HOURS` 默认 4，允许 2 至 24 的整数；
- `TREND_X_WOEIDS` 是逗号分隔的 TwitterAPI.io 趋势地区 ID，默认 `1` 表示全球；
- `TREND_YOUTUBE_REGION` 使用两位地区代码，默认 `US`；
- `TREND_REDDIT_COMMUNITIES` 只接受社区名称，不接受完整 URL；
- `TREND_GOOGLE_RSS_URLS` 是逗号分隔的 HTTPS Trending RSS 地址。

所有配置只在 API 和 Worker 服务端读取。`.env.example` 使用空值或明确的非敏感默认值，真实 Key 和私有 Feed URL 不提交版本库。

## 11. 错误处理与降级

- 单个趋势源失败不阻断其他趋势源；
- 趋势源成功但没有合格种子时，运行成功且新增数为 0；
- 趋势榜单可用但后续验证找不到事实支持时，不创建 RadarItem；
- OpenRouter 评审失败时，本次运行失败且不保存半成品；
- 手动刷新请求重复时复用现有排队状态，不产生并发任务；
- 前端轮询失败时停止旋转并显示刷新状态不可确认，保留当前 Feed；
- 外部正文、密钥、Authorization、趋势源完整响应和内部错误不得进入 API、数据库公开字段或浏览器日志。

## 12. 测试策略

### 12.1 Contracts 与 API

- 时间范围 schema 接受六个值并拒绝非法值；
- Feed 默认使用 `30d`，并正确组合 kind、topicId 和 origin；
- Topic 返回最新运行摘要且保持用户所有权；
- Trend 状态和手动刷新仅作用于当前用户；
- Topic 与 Radar 条目合并后按有效时间稳定排序；
- Item 详情不能跨用户读取。

### 12.2 Worker 与 Domain

- 版本型关键词不会被扩展成宽泛查询；
- 候选未命中完整关键词或确认别名时被拒绝；
- 每个趋势适配器解析结构化榜单、限制候选并映射安全错误；
- TrendSeed 去重且不保存榜单排名和完整响应；
- 非技术趋势在垂直筛选阶段被拒绝；
- 榜单标题没有正文支持时不会产生 RadarItem；
- 官方发布、作者原帖、Release 和论文能够通过；
- 单趋势源失败不影响其他来源；
- 调度租约、手动待处理和 4 小时周期可恢复且不重复执行。

### 12.3 Web

- Feed 刷新期间图标旋转并保持按钮尺寸；
- Topic 行只旋转当前刷新项；
- 完成提示准确展示新增、零新增、部分失败和全部失败；
- 下拉刷新只在顶部并越过阈值时触发；
- 时间筛选请求使用正确 query 参数；
- 所有发现视图按时间互斥分组；
- 趋势内容和 Topic 内容显示正确来源标记；
- 减少动画偏好和 `aria-live` 行为可访问。

### 12.4 端到端与回归

Playwright Fake 流程覆盖：

- 点击刷新到新增数量提示的完整生命周期；
- 移动端下拉刷新；
- 近 3 天和近 30 天筛选；
- Topic 与趋势内容混合、筛选和时间分组；
- 桌面、平板、手机和 320px 紧凑视口无重叠或文字溢出。

最终验证仍包括 Prisma 生成与迁移、lint、typecheck、单元/集成测试、生产构建和端到端测试。外部实时趋势测试必须显式启用并提供对应凭据，默认测试不访问外网。

## 13. 非目标

- 不提供用户自定义可信等级、来源权重或榜单权重；
- 不展示事实核验标签、证据数量或内部 AI 判断；
- 不抓取需要个人 Cookie、验证码或模拟登录的趋势页面；
- 不承诺对所有新闻类别进行通用热点监控；自动趋势聚焦技术、AI、软件产品和研究；
- 不在本次增加邮件、Push 或其他通知渠道；完成提示仅在当前 Web 会话中展示。

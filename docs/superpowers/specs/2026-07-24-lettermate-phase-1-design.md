## 1. 目标与范围

第一阶段交付“可信事件发现与通知”端到端闭环：用户创建关键词监控规则，系统从合规 RSS 和许可网页采集公开内容，完成标准化、去重、事件聚类与确定性可信度判定，并在响应式 Web 页面中展示事件、证据链和通知。符合条件的高优先级已确认事件可触发浏览器 Push。

本阶段包含：

- 个人账号、会话、用户数据隔离和个人数据删除；
- 关键词、同义词、排除词、监控范围、优先级和即时通知配置；
- RSS 与经合规审核的网页来源采集；
- 内容标准化、去重、规则匹配、事件聚类、摘要和风险提示；
- 已确认、待核实、已驳回三种可信状态及完整证据链；
- 首页事件流、监控规则、事件详情、通知中心、来源状态和个人设置；
- 站内通知与浏览器 Push；
- 采集任务、限频、退避、失败原因与处理耗时的可观测性。

以下能力延后到后续阶段，但在接口和数据模型中保留扩展边界：

- X、B 站及其他社交平台采集；
- 创作者订阅、分组与每日邮件摘要；
- 个性化推荐、探索配额及反馈学习；
- 团队、付费、复杂运营后台和全网搜索。

## 2. 技术选型

采用前后端分离架构，各运行单元独立构建和部署。

| 领域 | 选择 | 理由 |
| --- | --- | --- |
| Web | React、TypeScript、Vite | 产品是登录后的工作台，无首期 SEO 需求；SPA 部署简单，适合独立 API。 |
| UI 与状态 | React Router、TanStack Query、React Hook Form、Zod | 路由、服务端状态、表单和运行时校验职责清晰。 |
| API | NestJS、TypeScript、REST、OpenAPI | 模块边界明确，可生成稳定契约，并与 Worker 共享领域类型。 |
| ORM | Prisma | 迁移、类型安全查询和事务 API 适合首期团队规模。 |
| 主数据库 | PostgreSQL | 支持事务、约束、JSON 元数据、全文检索和审计查询。 |
| 队列 | Redis、BullMQ | 提供任务并发、来源级限流、延迟、重试和指数退避。 |
| Worker | 独立 NestJS 进程 | 采集与分析负载不会阻塞用户 API，可单独扩缩。 |
| 浏览器通知 | Web Push、VAPID、Service Worker | 使用浏览器标准能力，不绑定单一推送厂商。 |
| 可观测性 | 结构化日志、OpenTelemetry、Prometheus 兼容指标 | 统一关联 API、任务、来源与事件处理链路。 |
| 测试 | Vitest、Testing Library、Supertest、Testcontainers、Playwright | 覆盖单元、API、真实依赖集成和跨端验收。 |

首期不拆为微服务。API 与 Worker 是两个部署进程，但共享同一后端代码库中的领域模块和数据库模型。只有当采集规模、语言需求或团队边界形成明确压力时，才拆分独立服务。

## 3. 系统架构

```text
Browser
  | HTTPS REST / Web Push
  v
React Web ---- Service Worker
  |
  v
NestJS API ----------------------+
  |                              |
  | transaction                  | enqueue after commit
  v                              v
PostgreSQL <---- Outbox ---- Redis / BullMQ
  ^                              |
  | transaction                  v
  +------------------------ NestJS Worker
                                  |
                                  v
                         RSS / Allowed Web Sources
                                  |
                                  v
                         Optional AI Provider
```

### 3.1 Web

Web 负责页面呈现、表单校验、查询缓存、会话状态、站内通知状态和 Push 授权。它不在浏览器中保存来源凭证、AI 密钥或长期访问令牌，也不执行可信度判定。

### 3.2 API

API 负责认证授权、用户隔离、监控规则、事件和证据查询、通知读写、来源状态查询及 Push 订阅管理。API 只执行短事务，不同步抓取网页或调用 AI。

### 3.3 Worker

Worker 负责定时调度、来源采集、标准化、用户规则匹配、事件聚类、AI 辅助分析、可信度规则计算和 Push 投递。不同来源使用独立队列或来源级并发键；一个来源的失败不会阻塞其他来源。

### 3.4 PostgreSQL 与 Outbox

PostgreSQL 是业务事实的唯一权威存储。Redis 只保存可重建的任务执行状态，不能保存事件最终状态或通知唯一性结论。

需要异步处理的业务变更采用事务 Outbox：事件状态、通知记录和 Outbox 消息在同一事务中写入；分发器将未投递消息加入 BullMQ，成功后标记已分发。消费者必须幂等，重复投递不会产生重复事件或通知。

## 4. 模块边界

后端按职责划分以下模块：

- `Auth`：注册、登录、注销、会话、密码哈希和账号删除；
- `Users`：邮箱、时区和通知偏好；
- `MonitorRules`：规则 CRUD、启停、同义词、排除词、范围和优先级；
- `Sources`：来源等级、独立性分组、合规状态、抓取策略和运行状态；
- `Collectors`：RSS 与网页采集适配器、调度、限频和退避；
- `Contents`：URL 规范化、内容指纹、元数据提取和重复检测；
- `Events`：聚类、证据关联、状态计算、状态历史和摘要；
- `RuleMatches`：用户规则与公开内容/事件的命中关系；
- `Notifications`：站内通知、去重、免打扰判定和 Push；
- `Outbox`：可靠异步消息分发；
- `Observability`：采集运行、错误分类、指标和链路关联。

采集器遵循统一接口，输入为来源策略和游标，输出标准化前的采集结果与下一游标。平台特有字段只保存在受控元数据中，不泄漏到事件判定核心。

## 5. 数据设计

### 5.1 主要实体

| 实体 | 关键字段与约束 |
| --- | --- |
| `User` | 邮箱唯一、密码哈希、时区、免打扰开始/结束时间、状态、创建时间；删除采用异步清理任务。 |
| `Session` | 随机令牌哈希、用户、到期时间、撤销时间；原始令牌只存在于 HttpOnly Cookie。 |
| `MonitorRule` | `userId`、名称、关键词、同义词、排除词、范围、优先级、通知开关、启停状态。范围只能是全部许可来源、指定来源类型集合或指定来源 ID 集合。 |
| `Source` | 类型、名称、基础 URL、可信等级、`independenceGroup`、合规状态、抓取策略。 |
| `CollectorRun` | 来源、开始/结束时间、结果、HTTP 状态、条目数、重试次数、错误分类和下次运行时间。 |
| `CandidateContent` | 来源、规范 URL、内容指纹、标题、作者、发布时间、抓取时间、正文、语言和元数据。 |
| `Event` | 主体、动作、时间窗口、可信状态、首发时间、最后发现时间、最后更新时间、摘要版本。 |
| `EventEvidence` | 事件、内容、支持/反驳、证据等级、独立性键、关联置信度。 |
| `EventStatusHistory` | 事件、前后状态、规则版本、理由、证据快照和变更时间。 |
| `RuleMatch` | 用户、规则、事件、匹配原因、首次/最后命中时间；组合唯一防止重复。 |
| `Notification` | 用户、事件、类型、状态、去重键、已读时间和投递时间；去重键唯一。 |
| `PushSubscription` | 用户、endpoint、加密密钥、创建/失效时间；敏感字段加密保存。 |
| `OutboxMessage` | 类型、聚合 ID、载荷、创建、分发、重试和错误信息。 |

### 5.2 共享与隔离

`Source`、`CandidateContent`、`Event` 和证据是公开内容形成的共享数据，避免为每个用户重复采集。`MonitorRule`、`RuleMatch`、`Notification`、`PushSubscription`、会话和偏好全部按 `userId` 隔离。

所有用户域查询必须由认证上下文注入 `userId`，Repository 不接受客户端提供的任意用户 ID。数据库为关键用户表建立包含 `userId` 的索引和组合唯一约束。端到端测试必须覆盖跨用户读取与修改均返回不可见结果。

## 6. 采集与合规

### 6.1 来源准入

来源具有 `pending`、`allowed`、`blocked` 三种合规状态。只有 `allowed` 来源可进入调度。来源配置保存：

- 适用服务条款与审核日期；
- `robots.txt` 最近检查时间和结果；
- 允许路径、禁止路径、User-Agent 和联系信息；
- 最小采集间隔、并发数、超时、缓存时间和最大正文大小；
- 限频与失败退避策略。

RSS 可按明确 feed 地址接入。网页采集只允许预先配置的主机和路径，不提供用户任意 URL 通用爬取，不绕过登录、验证码、付费墙、Cloudflare 或其他访问控制。首期只获取服务端可返回的公开 HTML，不运行无头浏览器绕过限制。

首期来源通过版本化种子配置和数据库迁移维护，不建设复杂运营后台。用户可以在许可来源中限定监控范围，但不能新增来源、改变可信等级、修改独立性分组或绕过合规状态。

### 6.2 稳定性

每个来源使用独立调度键、并发限制和熔断状态。HTTP 429、5xx、网络超时、解析失败和合规阻断分类记录：

- 429 遵守 `Retry-After`，否则指数退避并加随机抖动；
- 连续失败达到阈值后暂停来源并展示原因；
- 304 或内容未变化只更新运行记录，不重复分析；
- 单次响应超过大小或超时上限时终止处理；
- 解析器异常只影响当前条目和来源任务。

## 7. 内容处理与事件状态

### 7.1 处理流水线

```text
采集 -> URL 规范化 -> 内容指纹去重 -> 元数据提取
     -> 用户规则匹配 -> 实体/动作/时间提取 -> 候选聚类
     -> 证据独立性计算 -> 可信度规则 -> 摘要
     -> 事件与历史事务提交 -> 通知 Outbox
```

URL 去除已知跟踪参数并遵守 canonical URL；完全相同内容使用规范文本哈希去重。事件聚类使用“主体、动作、时间窗口”的确定性特征和语义相似度。低于自动合并阈值的内容创建独立待核实事件，不进行高风险强制合并。

### 7.2 可信状态机

内部处理进度与对外可信状态分离。对外只暴露：

- `pending`（待核实）：只有单一非原始来源，或证据不足；
- `confirmed`（已确认）：一级来源直接发布，或至少两个独立二级来源交叉佐证；
- `rejected`（已驳回）：来源不可信、主体/关键时间冲突，或存在明确权威反证。

相同内容指纹、同一转载链或同一 `independenceGroup` 的内容只计为一个独立来源。兴趣来源只能用于发现，不能增加确认计数。

允许 `pending -> confirmed/rejected`。已确认事件出现权威反证时允许 `confirmed -> rejected`，但必须保存状态历史、证据快照和规则版本，并向已接收原通知的用户生成一次更正通知，禁止静默覆盖。

### 7.3 AI 边界与降级

AI 通过 `AiAnalysisProvider` 接口提供实体/动作建议、语义相似度、中文摘要和风险提示。供应商、模型、超时和限额由环境配置；请求不包含用户密码、邮箱或 Push 密钥。

AI 输出必须保存模型标识、分析版本和输入内容哈希。AI 不能直接写入可信状态。可信状态只由版本化确定性规则读取证据后计算。

AI 超时或不可用时，流水线继续保存内容、规则命中和可信状态，页面显示“摘要暂不可用”，任务进入有上限的重试；不得把 AI 故障描述为来源故障，也不得阻塞已具备充分证据的事件确认。

## 8. API 与认证

API 使用 `/api/v1` 前缀并发布 OpenAPI 文档。前端客户端由契约生成或通过共享 schema 校验，禁止手写不受验证的响应类型。

主要资源：

- `/auth/register`、`/auth/login`、`/auth/logout`、`/auth/session`；
- `/monitor-rules`：创建、查询、修改、暂停和删除；
- `/events`、`/events/:id`：事件流、筛选、时间线和证据；
- `/notifications`、`/notifications/:id/read`：通知查询和已读；
- `/push-subscriptions`：注册、刷新和删除 Push 订阅；
- `/sources`、`/sources/:id/runs`：来源等级、状态和近期运行；
- `/profile`、`/profile/data-deletion`：账户设置与个人数据删除。

认证采用短期服务端会话，随机会话令牌只通过 `Secure`、`HttpOnly`、`SameSite=Lax` Cookie 传输，数据库只保存令牌哈希。生产环境由同一站点下的反向代理提供 Web 与 API，CORS 仅允许配置的前端源并携带凭据。所有变更请求验证 `Origin` 和 CSRF Token。

API 错误采用统一结构：错误码、可安全展示的消息、字段错误和 `traceId`。服务端日志保留详细原因，但不回传堆栈、连接串、密钥或上游正文。

## 9. 通知设计

规则命中后，只有同时满足以下条件才生成即时事件通知：

- 规则启用即时通知且优先级为高；
- 事件状态为已确认；
- 作者、主题和来源未被用户规则排除；
- 相同用户与事件尚未发送同类型通知。

普通通知去重键为 `userId:eventId:confirmed`。重大新证据或更正通知包含证据修订号，每个修订只发送一次。

站内通知在业务事务中创建。Push 由 Outbox 异步投递，失败不会回滚站内通知；临时错误按上限重试，410/404 endpoint 标记失效。浏览器未授权或不支持 Push 时，页面明确保留站内通知能力，不宣称已开启即时 Push。

免打扰时间按用户时区计算。命中免打扰时间时仍立即创建站内通知，但 Push 延迟到免打扰结束；更正通知遵守相同规则。跨越午夜的时间段按一个连续区间处理。用户修改时区或免打扰设置后，尚未投递的 Push 按新设置重新计算。

## 10. 前端信息架构

应用采用工作台式布局，桌面端为固定侧栏加主内容区，移动端为紧凑顶栏和底部主导航。页面不使用营销式首页。

- **首页事件流：** 按最近更新展示事件，支持状态、规则和未读筛选；卡片显示状态、摘要、来源数量、更新时间和推荐原因；
- **监控规则：** 列表与编辑表单，显示启停、优先级、通知状态和最近命中；
- **事件详情：** 摘要、可信状态、判定理由、时间线和证据来源；外链始终显示来源归属；
- **通知中心：** 未读/已读、通知类型、事件状态与证据跳转；
- **来源说明：** 来源等级、合规状态、最近成功、失败原因、退避和停用状态；
- **个人设置：** 邮箱、时区、Push 授权、会话与个人数据删除。

状态不能只靠颜色表达；已确认、待核实、已驳回均同时显示图标和文字。异步页面提供加载、空状态、失败与重试。所有关键操作支持键盘，焦点可见，表单错误与字段关联。桌面、平板和手机断点均不得遮挡证据、操作或长 URL。

## 11. 安全与隐私

- 密码使用 Argon2id 哈希；登录和注册按 IP 与账号限频；
- HTML 正文经过服务端清洗后再展示，外链使用安全的 `rel` 属性；
- 抓取器阻止访问 loopback、私网、链路本地、云元数据地址和非 HTTP(S) 协议，防止 SSRF；
- 来源 URL 每次重定向后重新校验主机和地址，设置响应大小、重定向次数与超时上限；
- 密钥通过运行环境注入，不写入仓库、日志或数据库明文字段；
- Push 加密字段和必要敏感配置使用应用层加密；
- 删除账户后撤销会话，删除用户规则、命中、通知和 Push 数据；共享公开内容不携带用户身份，可继续保留；
- 审计日志不记录密码、Cookie、完整 AI 密钥或个人通知载荷。

## 12. 可观测性与性能目标

每个 API 请求、队列任务、采集运行和事件修订都携带 `traceId`。指标至少包括：

- 来源最近成功时间、成功率、429/5xx/解析失败数、熔断状态；
- 队列等待时间、执行时间、重试数和死信数；
- 从首次成功采集到事件落库、确认和通知入队的耗时；
- Push 成功、临时失败和失效订阅数；
- AI 调用耗时、失败率和降级次数。

需求中的 10 分钟目标定义为：内容已被一次成功采集后，在 10 分钟内完成事件创建；满足确认条件且命中高优先级规则时，在同一窗口内生成站内通知并把 Push 加入投递队列。采集周期本身按来源合规策略配置，不承诺突破平台允许频率。

## 13. 测试策略

### 13.1 单元测试

- 关键词、同义词、排除词与范围匹配；
- URL 规范化、内容指纹和转载去重；
- 独立来源计数与三态可信度规则；
- 状态迁移、通知条件、去重键和更正通知；
- 限频、指数退避、熔断与 AI 降级。

### 13.2 集成与契约测试

- 使用真实 PostgreSQL 与 Redis 容器验证迁移、事务 Outbox、队列重试和消费者幂等；
- 使用本地 HTTP fixture 验证 RSS、robots、重定向、超时、大小限制和 SSRF 防护；
- OpenAPI 与前端客户端契约校验；
- 两用户数据隔离、会话撤销、CSRF、账号删除和 Push endpoint 失效处理。
- 监控范围三种模式、跨午夜免打扰以及时区变更后的延迟 Push 重算。

### 13.3 端到端与视觉测试

Playwright 覆盖注册登录、创建规则、命中事件、查看证据、接收/阅读通知、查看来源故障和删除账户。使用桌面、平板与手机视口执行，检查文本溢出、遮挡、键盘焦点和关键操作可达性。

Push 在测试环境使用可控适配器验证投递与去重；浏览器授权流程另做 Chromium 集成测试。AI 使用确定性 fake provider，另外提供受环境开关控制的供应商冒烟测试，避免常规测试依赖外部费用与网络。

### 13.4 验收场景

1. 创建高优先级关键词规则后，测试来源内容形成事件并可查看；
2. 一级来源直接确认，两个独立二级来源交叉确认，单一二级来源保持待核实；
3. 两篇转载只形成一个证据计数，不重复通知；
4. 已确认事件展示一级来源或至少两个独立二级来源；
5. 高优先级已确认事件生成一次站内通知和一次 Push 投递；
6. 来源受限、限频或失败时，来源页显示真实状态且其他来源继续运行；
7. 手机、平板和桌面均可完成规则配置、事件证据阅读和通知设置；
8. 从成功采集到符合条件的通知入队在 10 分钟内完成；
9. 用户 A 不能读取或修改用户 B 的规则、通知、会话和 Push 数据；
10. AI 不可用时仍能完成采集、事件判定和通知，页面明确显示摘要降级状态。

## 14. 部署与开发环境

代码仓库采用工作区结构：

```text
apps/web       React Web
apps/api       NestJS API
apps/worker    NestJS Worker
packages/contracts   API schema 与生成类型
packages/domain      无框架的领域规则
packages/config      共享配置校验
infra                容器与部署配置
```

本地使用 Docker Compose 启动 PostgreSQL 和 Redis，Web、API、Worker 可在宿主机热更新运行。测试使用独立数据库和 Redis 命名空间，禁止连接开发或生产数据。

生产部署至少包含 Web 静态站点、API 容器、Worker 容器、托管 PostgreSQL、Redis 和 HTTPS 反向代理。迁移由单独发布步骤执行；Worker 与 API 只有在迁移成功后滚动更新。备份与恢复演练覆盖 PostgreSQL；Redis 不作为需要恢复的业务事实存储。

## 15. 分阶段实施边界

实施计划将按可独立验证的纵向增量拆分：

1. 工程基础、认证、用户隔离和契约；
2. 来源配置、RSS/网页采集、运行状态和安全边界；
3. 关键词规则、内容标准化与命中；
4. 事件聚类、证据链、可信状态和 AI 降级；
5. 站内通知、事务 Outbox 与浏览器 Push；
6. 响应式页面完善、端到端测试、性能与验收测试。

每个增量先写失败测试，再实现最小代码，通过该增量测试后提交人工可验证结果。任何外部服务凭证、来源合规审批或部署域名缺失时，使用本地适配器完成开发，但不会把模拟结果表述为真实外部投递。

## 16. 设计决策摘要

- 选择前后端分离，但首期保持模块化单体后端，避免过早微服务化；
- PostgreSQL 是事件、证据和通知的唯一事实来源，BullMQ 仅承担任务执行；
- 共享公开事件数据，严格隔离用户规则、命中、通知和凭证；
- 网页采集必须经过来源准入，不支持任意 URL 通用爬取；
- AI 辅助分析但不能决定事件已确认状态，AI 故障不会阻断可信规则；
- 事务 Outbox、幂等消费者和唯一去重键共同保证通知不丢失、不重复；
- 首期完成可信事件闭环，社交平台、邮件和推荐在后续独立规格中实现。

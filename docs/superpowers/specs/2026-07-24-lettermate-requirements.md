**版本：** V1.0
**日期：** 2026-07-24
**状态：** 已确认，技术设计已批准

## 1. 背景与目标

目标用户是需要及时跟踪 AI、技术及个人兴趣信息的学生兼开发者。用户不应仅依赖手工搜索，而应借助系统自动发现新热点、关注创作者的更新和潜在感兴趣的优质内容。

产品以响应式 Web 应用形式交付，首期目标是：

- 尽早发现用户指定主题的可信新事件；
- 给出可复核的事实状态、来源和摘要；
- 聚合关注创作者的更新并通过每日邮件推送；
- 依据明确反馈持续优化推荐，同时保留有限的信息探索；
- 通过浏览器即时通知推送高优先级、已确认的事件。

## 2. 术语

| 术语 | 定义 |
| --- | --- |
| 候选内容 | 由采集器获取、尚未完成事件聚类与可信度判定的网页或社交内容。 |
| 事件 | 围绕同一主体、动作和时间范围聚合的候选内容集合。 |
| 独立来源 | 不属于同一转载链、且拥有独立采集或发布能力的来源。转述同一篇报道的页面不计为多个独立来源。 |
| 一级来源 | 事件主体直接发布的官方原始材料。 |
| 二级来源 | 经运营维护白名单认可的独立媒体报道。 |
| 兴趣来源 | 用于发现和推荐的创作者或社区，不自动构成事实确认依据。 |

## 3. 范围与非目标

### 3.1 MVP 范围

- 合规网页采集、X 数据接口和 RSS 等多通道内容发现。
- 用户关键词监控与事件通知。
- 关注的创作者更新聚合与每日摘要。
- 显式偏好反馈、个性化推荐和有限探索推荐。
- 站内通知、浏览器 Push 与每日邮件摘要。
- 响应式 Web 页面。

### 3.2 非目标

- 社交发布、评论互动或私信。
- 绕过登录、验证码、付费墙或站点访问限制。
- 自动化的全网舆情分析。
- 付费订阅、团队协作和复杂的运营后台。
- 将 AI 单独判定作为事实确认结论。

## 4. 信息来源与采集规则

### 4.1 数据通道

- 网页采集：采集可公开访问、允许采集的目标页面。搜索仅用于发现候选 URL；搜索结果页和转载内容不作为事实依据。
- X：通过 [twitterapi.io](https://twitterapi.io/) 获取公开内容、用户关注账号的更新和候选事件线索。
- RSS：优先接入来源明确且更新稳定的官方或媒体 RSS。
- B 站：采集官方账号、用户关注创作者、指定分区和关键词检索结果中的视频/动态标题、简介、发布时间、作者主页与原始链接。评论区只用于发现线索，不参与事实确认。

### 4.2 来源等级

| 等级 | 用途 | 示例 |
| --- | --- | --- |
| 一级来源 | 可直接确认事件 | 事件主体官网、新闻稿、官方博客、GitHub Release、论文或研究机构页面、人工核验的 X/B 站官方账号。 |
| 二级来源 | 与其他独立来源交叉确认 | 路透、美联社、BBC、The Verge、TechCrunch、Ars Technica，以及机器之心、量子位、InfoQ 中文、36 氪等可维护白名单。 |
| 兴趣来源 | 发现、订阅与推荐 | 用户关注的 X/B 站创作者、知乎、掘金、V2EX、开源中国、少数派等。 |

来源白名单必须可配置。每条内容必须保存原始 URL、作者、发布时间、抓取时间、来源类型和可信等级。

### 4.3 合规与稳定性

- 每个平台独立配置抓取频率、缓存时长、错误退避策略和允许的路径。
- 采集器必须遵守目标站点适用的服务条款和 `robots.txt`；受限来源应停用对应采集器并在界面中展示状态。
- 不得通过技术手段规避访问控制。
- 同一来源故障不得阻塞其他来源采集。

## 5. 功能需求

### 5.1 关键词与热点发现

用户可以创建、编辑、暂停和删除监控规则。每条规则包含：

- 关键词及同义词；
- 排除词；
- 监控范围；
- 优先级；
- 是否启用即时通知。

系统应对候选内容进行语义匹配、实体识别和重复聚类，将同一事件的多个转载内容合并。事件页应展示时间线、来源数量、状态、AI 摘要和证据链接。

### 5.2 真实性与事件状态

AI 可用于语义匹配、实体识别、重复内容聚类、摘要生成和风险提示，但不能独自将事件标记为已确认。

| 状态 | 判定规则 |
| --- | --- |
| 已确认 | 一级来源直接发布，或至少两个独立二级来源对同一事件形成交叉佐证。 |
| 待核实 | 只有单一非原始来源，或证据不足。默认降低通知优先级。 |
| 已驳回 | 来源不可信、关键时间/主体不一致，或与权威材料存在明确冲突。 |

每个已确认事件必须能回溯到一级来源，或至少两个独立二级来源。系统应区分事件的首发时间、最后发现时间和最后更新日期。

### 5.3 博主订阅与摘要

用户可录入 X、B 站等平台的创作者主页 URL 或账号标识，并可分组管理。系统定期获取公开更新，生成包含以下内容的每日摘要：

- 新发布内容及原始跳转链接；
- 关键观点和简短中文摘要；
- 关联主题、已确认热点和用户偏好关联说明。

### 5.4 个性化推荐与探索

用户可以对内容执行喜欢、不感兴趣、收藏、屏蔽作者和屏蔽主题。显式反馈是推荐学习的主信号；阅读、点击与收藏可作为辅助信号。

默认推荐配额为 85% 已知偏好内容和 15% 探索内容。探索内容最多 3 条/日，且必须遵守用户的屏蔽作者、屏蔽主题及内容安全规则。系统应能够解释推荐的主要原因，例如“来自已关注创作者”或“与已收藏的 AI Agent 主题相关”。

### 5.5 通知

- 即时通知：站内通知和浏览器 Push。默认只对高优先级且状态为已确认的关键词事件推送。
- 每日摘要：按用户时区的指定时间发送邮件，内容包括关注创作者更新、推荐精选和未读热点。
- 事件去重：同一事件跨来源只发送一次即时通知；如出现重大新证据，可以发送一次更新提醒。
- 用户可设置关键词级别、通知开关、免打扰时间、每日邮件时间和邮件地址。

## 6. 页面与交互

- 登录与个人资料：邮箱、时区和浏览器通知授权。
- 首页信息流：热点、订阅内容和推荐内容。
- 关键词监控：规则配置和命中历史。
- 博主管理：录入、分组、更新状态和最近内容。
- 通知中心：通知状态、已读状态、证据与跳转链接。
- 偏好设置：反馈历史、屏蔽项、探索比例和通知设置。
- 来源说明：来源等级、采集状态、失败原因和事件证据链。

页面须适配手机、平板和桌面浏览器。跳转至外部内容时，应保留用户阅读状态和来源归属。

## 7. 核心数据流

1. 各来源采集器按各自调度策略获取公开候选内容。
2. 标准化处理提取作者、主题、实体、时间、链接和来源元数据。
3. AI 和规则引擎完成关键词匹配、聚类、摘要与风险提示。
4. 可信度规则将事件标记为已确认、待核实或已驳回。
5. 通知服务根据规则、优先级、去重和免打扰设置投递通知。
6. 推荐服务结合订阅、显式反馈和辅助行为信号构建首页和邮件摘要。

## 8. 非功能要求

- 关键词命中可信来源后，系统应在首次成功采集后的 10 分钟内创建事件并发送即时通知。
- 每日邮件应在用户配置的本地时间发送，包含可用的原始链接和未读内容。
- 每个采集器的失败、限频和停用状态必须可观测并在来源说明页展示。
- 用户偏好、订阅、邮箱和通知数据必须按用户隔离，并提供个人数据删除能力。
- 无法采集或来源受限时，界面必须明确说明状态，不得以“实时”或“已确认”误导用户。

## 9. 验收标准

1. 用户配置关键词后，来自可信来源的命中内容在 10 分钟内形成可查看事件；符合确认规则的高优先级事件触发浏览器即时通知。
2. 同一事件的多篇转载在信息流和通知中心聚合展示，不重复推送。
3. 每个已确认事件都能展示一级来源，或展示至少两个独立二级来源。
4. 用户录入 X/B 站创作者后，每日邮件包含其新增公开内容、中文摘要与原始链接。
5. 用户屏蔽作者或主题后，对应内容不再出现在推荐与通知中。
6. 手机、平板和桌面端均可完成关键词配置、博主订阅、反馈、阅读证据和通知设置。

## 10. 技术设计前的约束

- 首期支持个人账号和数据隔离；后续再评估团队协作和付费能力。
- 具体采集频率须按各平台服务条款和实际稳定性在技术设计阶段配置，不能以固定频率替代合规审查。
- X 数据使用受 twitterapi.io 的可用性、套餐和服务条款约束；系统须为该数据通道提供故障降级提示。

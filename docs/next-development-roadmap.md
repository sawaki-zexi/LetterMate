# LetterMate 开发路线图

**更新日期：** 2026-08-10

## 当前基线

已完成：

- 精确关键词监控、自动技术趋势和多来源质量管线；
- RSS/Atom、X、Bilibili、YouTube、Bluesky 博主关注；Bilibili 已覆盖公开视频、公开动态、专栏和带原帖上下文的转发动态，Bluesky 已覆盖原创、引用、转发和带父帖上下文的回复；
- 统一 Feed、显式反馈、兴趣记忆和个性化排序；
- 对现有候选的相邻兴趣识别、约 10% 探索编排和邮件禁入；主动相邻候选构造尚未开始；
- 每日邮件偏好、预览、调度、冻结快照、重试和运行状态；
- 每日邮件与兴趣记忆的跨 Topic/Trend/Creator 去重、直接兴趣排序和相邻探索排除闭环；
- 每日研究简报的结构化结论、证据、不确定性、后续关注点和冻结引用链；
- 生产 SMTP 适配器、未配置能力状态和显式 live smoke 入口。

## P0：生产身份（单实例基线已完成）

1. 已实现登录、登出、会话滑动续期和撤销。
2. 已使用 HttpOnly、生产 Secure、SameSite Cookie 承载服务端 Session。
3. 已为所有生产写操作增加 CSRF 防护。
4. 生产 Web 和业务接口不再接受固定 `x-user-id`；开发兼容由 `ALLOW_DEV_IDENTITY` 显式控制。
5. 已增加进程内登录限流、旧 scrypt 参数自动升级和跨用户回归测试；横向扩展 API 前需将限流状态迁移到 Redis。

完成条件：未认证请求不能访问用户资源；跨用户访问不泄露资源；浏览器不持有身份伪造头。

## P0：生产运行

1. 已实现统一结构化日志契约、API `x-trace-id`、错误响应 trace 复用，以及 Worker queue/job/run 事件。
2. 已实现分钟级队列快照、任务/来源安全失败事件、API/Worker 低基数 Prometheus 指标，以及可选 Prometheus Compose profile 和初始告警规则；目标环境仍需接入仪表盘、Alertmanager、通知渠道和日志聚合。
3. 已实现 PostgreSQL custom-format 备份、SHA-256 清单、14 日/8 周/12 月分层保留、Docker-socket-free direct 运维容器和隔离恢复验证；目标环境仍需配置每日调度、加密外部副本和周期演练通知。
4. 已实现脱敏 `ops:doctor` 配置/依赖诊断和密钥轮换、配额检查、故障恢复手册；目标环境仍需执行真实轮换并记录供应商配额基线。
5. 已实现存活/就绪探针、依赖异常 503、API/Worker 优雅退出，以及 API/Worker/Web 容器和一次性迁移 Compose 基线；目标环境仍需完成 TLS、秘密存储、容量基线和部署演练。

完成条件：可以发现故障、定位运行、恢复数据库并轮换密钥，而不暴露凭据或用户邮箱。

## P1：平台扩展

按真实使用需求选择，不阻塞生产上线：

1. 已实现 Bilibili 动态、专栏和转发动态，并提供显式 live smoke；
2. 已实现 YouTube Creator；
3. 已实现 Bluesky Creator，并提供离线测试和显式 live smoke。

每个平台必须先实现结构化身份解析、稳定账号 ID、公开内容增量、失败隔离和 live smoke，再进入 Web 能力列表。

## P1：兴趣效果观测

当前已完成第一条曝光观测闭环：Feed 决策 ID、浏览器可见曝光、API 所有权校验、分钟桶去重，以及 PostgreSQL/Memory 两套实现和测试。

下一步按以下顺序推进：

1. [x] 部署并验证 `FeedImpression` 迁移，确认生产数据库 schema 与应用版本一致；
2. [x] 汇总曝光、`interested`、`less` 和订阅保护数据，生成按日离线质量基线（`npm run evaluate:interest-effects -- YYYY-MM-DD`）；
3. [x] 增加推荐决策与曝光指标的低基数监控，并在拒绝率超过 10% 时告警；
4. 基线稳定后再评估相邻兴趣候选构造；暂不引入 embedding、在线学习或 bandit。

完成条件：可以回答“哪些推荐被看见、哪些被明确喜欢或减少、订阅内容是否始终保留”，且不跨用户、不突破精确关键词边界。

## P1：来源质量观测

1. [x] 按稳定 connector ID 和来源类型记录成功/失败尝试，不使用用户、关键词、URL 或运行 ID 标签；
2. [x] 记录候选获取、时间/正文/关键词/重复拒绝、事实支持、多样性和最终精选贡献；
3. [x] 为来源重复失败、成功但零候选、低精选率和单来源占比超过 90% 增加初始告警；
4. [x] 增加 `evaluate:source-quality`，从 Prometheus 的 24 小时 counter increase 和 Worker uptime range 生成 `healthy | review_required | insufficient_data` 报告；
5. [ ] 在目标环境积累完整 24 小时真实漏斗数据，校准最小 20 条候选、5% 精选率和 90% 单来源占比阈值。

完成条件：可以从指标判断来源没有贡献是因为配置/调用失败、零候选、正文或质量拒绝、去重，还是被其他来源长期挤占；任何遥测失败不得改变发现结果。

## P1：引用型中文研究简报

基础引用快照与结构化模板已经落地，下一步在不削弱回退能力的前提下增加来源约束的 AI 生成：

1. [x] 为每个结论保存原文 URL、来源平台、发布时间和对应候选内容键；
2. [x] 使用结构化模板保存“结论、证据、分歧/不确定性、后续关注点”，禁止无引用结论；
3. [x] 复用现有质量管线和兴趣排序，邮件最多 10 条，探索内容继续禁入；
4. [x] 覆盖引用完整性、重复发送和失败重试，并在预览页展示引用链；
5. [x] 新增来源约束的 AI 简报生成器：模型只返回稳定引用 ID，服务端验证引用属于冻结来源集合；
6. [x] AI 生成或校验失败时保留当前可读链接摘要，投递重试不得重新生成内容。

该阶段已完成。后续开发进入语义召回准入评估，不将生成式摘要当作新的兴趣事实或排序信号。

完成条件：每个结论都能跳转到已验证的原文，生成失败时保留可读的链接摘要，不发送无证据内容。

## P2：语义召回与受约束探索

只有在积累足够曝光与显式反馈后再实施。主动相邻候选构造也受同一真实数据基线约束：

1. [x] 使用现有结构化兴趣标签评估召回遗漏，形成无未来泄漏的离线 rolling split 基线（`npm run evaluate:semantic-recall -- YYYY-MM-DD 14`）；
2. 若标签召回确有稳定遗漏，再引入 pgvector 作为兴趣簇召回通道；
3. 所有向量候选仍必须经过来源证明、质量门控、精确关键词边界、订阅保护和跨用户隔离；
4. 探索比例保持约 10% 上限，暂不启用在线 bandit，直到负反馈和质量指标达到预设门槛。

完成条件：语义召回相对标签基线提升覆盖率，同时零跨用户泄露、零精确版本越界、零无证据 Feed 项。

当前准入状态：评估器已实现，但 2026-08-10 向前 14 天的真实数据库为 0 曝光、0 显式反馈，结论为 `insufficient_data`。默认门槛为 14 天、200 次有效曝光、30 条首次显式反馈和 10 条正反馈；同时要求订阅覆盖率为 100%、跨用户决策违规为 0。只有在至少 5 个语义缺口、缺口率不低于 15% 且分布于至少 3 个日期切片时，才建议进入 pgvector shadow 实现。

## 外部验收阻塞

代码侧生产监控和容器配置已完成，但当前 Docker 无法访问镜像仓库，因此尚未完成 Prometheus 官方校验、生产镜像构建、Prometheus/Alertmanager 启动和真实告警演练。网络或镜像仓库恢复后，应按 `docs/operations-runbook.md` 执行并记录结果，不将本地测试替代目标环境验收。

## 决策边界

当前 SMTP 通过确定性 `Message-ID` 尽力减少重试重复，但标准 SMTP 无法严格解决“已接受但确认丢失”。如果产品要求严格零重复，新增支持幂等键的供应商 HTTP API 适配器，并将 SMTP 保留为兼容模式。

- Prisma 变更包含迁移和 Client 生成；
